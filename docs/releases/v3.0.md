# GitHub Sentinel v3.0

> 第三个正式发布版本：按研发周期筛选的「项目研发周期报告」
> 对应标签 `v3.0`，包版本 `3.0.0`

v2.0 的每日动线只能回答「今天发生了什么」——窗口是订阅时区的一个自然日，回溯也只是把
同一个 `updated_at` 口径挪到昨天。管理层真正要的那份东西是另一种问法：

> 这个迭代（比如 11-01 到 11-15）**交付了什么**？

这两句话的差别不在时间跨度，而在**判定轴**：前者的入选条件是「这段时间被碰过」，
后者的入选条件是「这段时间**完成**了」。v3.0 把后者做成一等公民。

```
v2.0（活动口径）           updated_at ∈ [from, to+1d)         → 议题/PR 当天有新动静就算
v3.0（完成口径，默认）     merged_at / closed_at ∈ [from, to+1d) → 只算这段时间真正合入/关闭的
```

---

## 本版包含什么

### 1. 领域层：把「一段时间」和「选什么」分开建模

- `domain/period.py`：`ReportPeriod` 持有闭区间日期（人对「11-01 到 11-15」的理解含两端），
  换算成时间窗口时才变成左闭右开 `[from 00:00, to+1d 00:00)`，相邻两段区间不会在边界上重复计数。
  `file_stem()` 恒输出 `A_to_B`——单日区间（`--from 11-15 --to 11-15`）也如此，
  因为它的口径与 v2.0 的 `2026-11-15.md` 不同，两者必须能共存。
- `domain/selection.py`：`ReportSelection` 是「选什么」的唯一真相——口径枚举、入选谓词、
  排序轴、展示用的时间字段、文件名后缀、给模型的硬约束文案、指纹载荷，全部从这一处产出。
  模板和提示词不许另写一套判据，否则「文档说的一套、数据是另一套」是必然结果。

`selection` 刻意**不 import progress**：谓词用 `Protocol` 描述结构化类型，由 progress 单向依赖它。
反过来写会在运行时撞上循环 import。

### 2. 取数：REST 翻页 + 本地谓词，不引入新的限流域

GitHub 的 REST 端点对「完成时间」这件事几乎没有支持：`/pulls` 既不接受 `since`，
也没有 `state=merged`；`/issues` 的 `since` 只按 `updated_at` 过滤。所以策略是：

1. 服务端只下推它支持的：完成口径时把 `state` 设为 `closed`；
2. 翻页到「`updated_at` 早于区间起点」为止（**排序键与停止键都用 `updated_at`**）；
3. 再在本地按 `merged_at` / `closed_at` 过滤出真正本期完成的。

翻页剪枝现在有三件套：`stop_before`（整体停止）、`skip_before`（左端过滤但不停页）、
`skip_at_or_after`（右端过滤）。中间那个是给 `/releases` 用的——它按 `created_at` 排序而我们看
`published_at`，早停会漏掉「早建草稿、本期才发布」的版本。

### 3. 一个会静默漏报的设计错误（已规避 + 测试锁死）

最自然的实现是「既然按 `merged_at` 判定，那就让翻页也按 `merged_at` 停止」。它会这样出错：

```
服务端按 updated_at 倒序返回：
  PR-A  merged_at=10-20（很早）  updated_at=11-14（最近被评论）   ← 排第一
  PR-B  merged_at=11-10（本期）  updated_at=11-10                ← 排第二
翻到 A 时判断 merged_at < window_start → break
结果 B 永远不会被读到，报告静默漏掉一个本期合并的 PR
```

正确做法是让停止键保持 `updated_at`：`updated_at < start` 必然蕴含 `merged_at <= updated_at < start`，
用它停止是安全的；而 `merged_at` 本身与排序顺序无关，用它停止就是错的。
`tests/unit/test_rest_github.py::test_merged_axis_does_not_drop_prs_merged_inside_window`
把这个场景写成了断言「必须翻到第 2 页并收到 B」。

### 4. 服务层与 CLI：扩展命令，不新增子命令

```bash
sentinel.cli progress --repo fastapi/fastapi --from 2026-11-01 --to 2026-11-15
sentinel.cli report   --repo fastapi/fastapi --from 2026-11-01 --to 2026-11-15
sentinel.cli daily    --id 1 --from 2026-11-01 --to 2026-11-15 --merged
```

参数矩阵（模式由 **flag** 决定，不由日期形状决定，否则 `--date D --merged` 会悄悄覆盖单日产物）：

| 参数 | 含义 | 约束 |
|---|---|---|
| `--from A` | 区间起点 | 与 `--date` 互斥 |
| `--to B` | 区间终点（含当天） | 缺省今天；单独使用无效 |
| `--merged` | 只收已合并 PR | 需配 `--from` |
| `--closed` | 只收已关闭 Issue | 需配 `--from` |
| `--activity` | 退回 v2.0 的 `updated_at` 口径 | 需配 `--from`，与 `--merged/--closed` 互斥 |

只给 `--from/--to` 不给口径 = 默认完成口径（已合并 PR + 已关闭 Issue）。

产物按「区间 + 口径后缀」命名，默认口径不加后缀：

```
2026-11-01_to_2026-11-15.md            # 完成口径（默认）
2026-11-01_to_2026-11-15.merged.md     # --merged
2026-11-01_to_2026-11-15.closed.md     # --closed
2026-11-01_to_2026-11-15.activity.md   # --activity
```

同一区间的 `--merged` 与 `--closed` 是两份不同的交付清单，必须落不同文件，
否则会永久互相覆盖并让报告反复重算。

服务层的入口校验顺序也是刻意的：**所有参数错误都在任何 GitHub 请求之前拦掉**
（区间倒序、终点在未来、跨度超限、窗口尚未开始），否则白烧一次配额。

### 5. 渲染与提示词：口径必须同时体现在「数字」和「措辞」上

完成口径下不能再写「本日 N 个议题有更新」——那些对象本来就已经关闭了。所以：

- 统计表只保留交付类指标（关闭议题 / 合并 PR / 提交 / 发布 / 贡献者），去掉 open、draft 这类活动口径才有的行；
- 小节标题与时间列改成「已关闭 / 已合并」「关闭 / 合并」，取值走 `closed_at` / `merged_at`；
- 「数据口径」段落改由 `selection.criteria()` 生成，与谓词同源；
- 报告标题从「项目每日报告」变成「项目研发周期报告」；
- 系统提示词追加一条硬约束：「只统计区间内合并的 PR 与关闭的 Issue；区间之外发生的评论、推送等新活动
  不属于本期交付，不要写进关键进展。」——不写这条，模型看到明细里的旧评论就会编出「本周多次讨论」。
- 规则兜底的 headline 换成「本期 N 个议题关闭、N 个 PR 合并、N 个版本发布」，
  计划项换成核对交付清单 / 高风险改动回归验证。

**报告的口径以进展文件 front matter 为准**（`issue_axis` / `pull_axis`），不从本次参数读：
`report --from A --to B` 可能没带 `--merged`，但文件里已经写明它是完成口径，提示词必须与文件一致。

### 6. HTTP 接口

```
POST /api/v1/daily/period
{
  "repo_full_name": "fastapi/fastapi",
  "date_from": "2026-11-01",
  "date_to": "2026-11-15",
  "scope": "completion",        // completion | activity | merged | closed
  "include_report": true
}
```

响应带上 `period_label` / `scope_label` / `criteria` / `stats` / `trimmed` / `truncated` /
`report_path` / `report_model` / `report_degraded`——调用方不需要再读文件就能知道口径与降级情况。
没拆成两个端点是因为两步之间有隐式耦合（报告的口径从进展文件的 front matter 读），
拆开等于让调用方负责传递它，而传错一次就会拿到「合并清单 + 活动口径提示词」这种混合产物。

### 7. 顺手修掉的两个 v2.0 隐患

- **指纹含 `window_end` 导致重跑白调模型**。单日窗口的右端会被裁到「现在」，于是同一份数据
  隔几分钟重跑一次指纹就变了、报告就重新调一次模型。现在指纹不再包含窗口端点，
  改为包含 `date_from` / 口径轴 / 截断标记。
- **`truncated` 一词兼指两件事**。「展示条数到顶」和「翻页预算耗尽」是完全不同的可信度问题：
  前者统计仍可信，后者统计只是下界。现在拆成 `trimmed`（提示）与 `truncated`（警告），
  CLI 前者进 stdout、后者进 stderr，且都不改变退出码（否则批量任务全红、没人再看退出码）。

## 已知限制

- **完成口径依赖 `merged_at` / `closed_at` 的历史值**。若对象被重新打开（reopen），GitHub 会把
  `closed_at` 清空，那么它从本期交付清单里就消失了。这是数据源语义，不是本项目的取舍。
- **`/pulls` 不支持 `since`**，所以区间越长、翻页越多；跨度上限与页预算就是为此设的闸门。
  预算打满会以 `truncated` 明确告知（统计是下界），不会假装数据完整。
- **提交与发布不参与完成口径**：它们没有「合并/关闭」概念，仍按 `committed_at` / `published_at`
  落窗口，且只有在 `SENTINEL_DAILY_RESOURCES` 里开出来才会采集。
- 区间模式仍然是「当前状态接口 + 时间戳回溯」，不是严格历史快照。
- `replay` 模式、SMTP 真实投递、`alembic` 迁移、多进程租约仍在待办。

## 变更清单

**新增**

- 领域层：`period`（`ReportPeriod` / `resolve_period_window`）、`selection`（`ReportSelection` / 口径谓词）
- 端口层：`ProgressQuery` 的两个轴参数、`ProgressResult.skipped`、`DailyStorePort` 的 `stem`
- 应用层：进展与报告服务的 `period` / `selection` 分支
- 基础设施：`_paginate` 的 `skip_before`、区间产物命名与 front matter 回填、模板区间分支
- API：`POST /api/v1/daily/period`
- CLI：`--from` / `--to` / `--merged` / `--closed` / `--activity`
- 配置：三个 `report_range_*`

**修改**

- `DailyProgress` 增加 `date_from` / `issue_axis` / `pull_axis` / `trimmed`
- `progress_fingerprint` 不再包含窗口端点，改含口径轴与截断标记
- 完成口径的风险识别换成互补规则（已合并/已关闭带风险标签 → 建议回归验证）
- `daily_progress.md.j2` 的统计表改为标签迭代，表头与取值随口径变化
- 版本号三处同步为 `3.0.0`

**修复**

- 进展指纹含 `window_end`，导致同一份数据重跑时白调一次模型
- `truncated` 一词兼指「展示裁剪」与「翻页触顶」，现已拆成 `trimmed` / `truncated`
- `/releases` 原先用 `published_at` 做 `stop_before`，而服务端是按 `created_at` 排序的：
  「早建草稿、本期才发布」的版本会因为前一条的 `published_at` 已早于窗口起点而被早停漏掉。
  现在改成 `skip_before`（左端逐条丢弃但不停页）
